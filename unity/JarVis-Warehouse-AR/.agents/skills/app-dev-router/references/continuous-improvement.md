# Continuous improvement

1. Capture the actual failure/outcome, environment, revision and evidence layer. Do not promote an unverified hypothesis.
2. Classify: business-specific rule, project setting, valid reusable pattern, temporary workaround or technical debt.
3. Project-specific → update canonical project memory only. Reusable → propose a narrow change to the relevant skill/router rather than adding a universal rule or new module by default.
4. Include motivating scenario, applicability/exclusions, counterexample, affected dependency/gate and regression test. Preserve user scope/approval boundaries.
5. Review and validate package, route behavior and portable isolation. Do not automatically modify global skills or other projects.
6. Keep old evidence dated, mark supersession, and stop accumulation of generic handoffs or duplicated instructions.

Examples of improved procedure: real audio device selection instead of array index; human audible acceptance separate from fixture timers; current capability check separate from historical release health; persistence explicit before production data; fresh results tied to inputs; prototype approval before application. Device names, warehouse rules, viewport, provider model or paid plan from one app are not universal defaults.
